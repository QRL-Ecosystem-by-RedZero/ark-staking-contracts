# Ark Staking

A yield-bearing position anchored in a one-way escrow on its origin chain, and a
catastrophe bond on QRL whose principal stands behind it. Hyperion contracts for
**QRL Zond**.

The escrow has no owner, no upgrade path and no function that accepts an
origin-chain signature as authority. Q-Day recovers keys; it does not alter
deployed bytecode, and a contract holds no key from which anything can be
recovered. Release of principal is initiated only by an ML-DSA-87-signed
instruction on QRL, and closes permanently once Q-Day is declared.

The position keeps earning. Its gross yield is split four ways at the origin
chain — staker, premium, buffer, operations — and the premium share is swept to
QRL to pay the bond's coupon. That share is not fixed: it is the target share
scaled by the fraction of the anchored notional the outstanding bond actually
covers, so a position pays for cover in proportion to the cover it receives, and
pays nothing when none has been sold.

**The specification of record is the Ark Staking yellow paper**
(<https://docs.quantumark.fi/docs/staking-yellow-paper>); the Technical
Reference beside it is normative for the interface, parameters and invariants, and
the whitepaper is a summary. Where this repository and the yellow paper disagree on
mechanism, the paper is right. `CLAUDE.md` has the details.

## Status

Both legs are built and under test: the QRL leg in `contracts/` and the
origin-chain escrow and relay in `ecdsa-stakings/`. `CLAUDE.md` §8.1 has the
inventory.

Also in `contracts/` are `ArkToken`, `VeArk` and `StakingVault`: stale v1 copies

## Quick start

```bash
npm install
npm run build     # vendor OpenZeppelin 4.9.6 -> .hyp, then compile with hypc
npm test          # the QRL-leg suite on a local ZVM harness
npm run gas       # gas profile of the main flows
```

`npm run check` (build + test) is the gate before any commit.

To run against a real multi-node Zond chain, see `CLAUDE.md` §4.2 — it needs WSL
and Docker, and the enclave is brought up from inside the distro.

## Two things that surprise people

**This is not Solidity.** Sources are `.hyp`, the pragma is
`pragma hyperion >=0.0.1`, the compiler is `@theqrl/hypc`, bytecode comes out
under `zvm` rather than `evm`, RPC is `qrl_*`, and addresses are printed with a
`Q` prefix. Accounts are ML-DSA-87, so there is no secp256k1 key anywhere.

**Neither chain can check the other's signatures**, and the relay is shaped
entirely by that. QRL has no `ecrecover` — signature recovery is meaningless when
every account is post-quantum — so a fact about the origin chain arrives as proof
of *state*, never proof of authorisation. The origin chain has no ML-DSA-87
precompile and a software implementation exceeds a block's gas limit, so the
escrow checks a *commitment*: the release payload is signed on QRL and sealed
into an epoch root the escrow has already accepted, and a substituted destination
produces no membership proof. `CLAUDE.md` §1.2 and §7.6 have the details.

## Layout

```
contracts/           the Ark Staking QRL leg — see CLAUDE.md §8.1
                     plus stale copies of ArkToken, VeArk, StakingVault — see CLAUDE.md §8.2
  interfaces/        their interfaces, plus IArkGovernor / IDisputeCourt / IRepScore
  lib/openzeppelin/  generated by npm run vendor — never hand-edit
scripts/             compile, vendor, deploy, gas, and the Kurtosis network stack
test/                the ZVM harness, one file per contract, and ArkStakeSpec
                     — every worked figure of whitepaper chapter 7
```

The origin-chain escrow is EVM bytecode, not ZVM, so it has its own compiler and
build under `ecdsa-stakings/` — do not add a Solidity file to `contracts/`.
